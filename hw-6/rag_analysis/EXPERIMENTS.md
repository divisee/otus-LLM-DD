## 1. Введение

Данный отчёт описывает эксперименты по оценке качества **retrieval-компоненты** RAG-системы для подбора фильмов. 

**Цель**: сравнить различные методы поиска и выбрать оптимальную конфигурацию для production.

**Датасет**:
- **Корпус**: 477 фильмов из Kinopoisk/IMDb
- **Вопросы для оценки**: 100 запросов разной сложности (1-5)
- **Формат вопросов**: косвенные описания фильмов без упоминания названий, актёров, цитат

## 2. Методология

### 2.1 Архитектура Retrieval

```
┌─────────────────────────────────────────────────────────────┐
│                        Query                                 │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
┌─────────────────────────┐     ┌─────────────────────────┐
│   Vector Retriever       │     │   BM25 Retriever        │
│   (Qdrant + Ollama)      │     │   (TF-IDF на text_ru)   │
│   cosine similarity      │     │   лексическое сходство  │
└─────────────────────────┘     └─────────────────────────┘
              │                               │
              └───────────────┬───────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    Score Fusion                              │
│   ┌─────────────┐   ┌─────────────┐                         │
│   │     RRF     │   │    DBSF     │                         │
│   │  (по рангам)│   │ (по скорам) │                         │
│   └─────────────┘   └─────────────┘                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│              Top-K Documents (ranked)                        │
└─────────────────────────────────────────────────────────────┘
```

**Компоненты:**

| Компонент | Технология | Описание |
|-----------|------------|----------|
| Vector Store | Qdrant | Хранение эмбеддингов, ANN-поиск |
| Embeddings | Ollama (embeddinggemma) | Локальная модель для генерации векторов |
| BM25 Index | In-memory | Классический лексический поиск |
| Fusion | RRF / DBSF | Объединение результатов двух retriever'ов |

### 2.2 DBSF — Distribution-Based Score Fusion

**Проблема RRF**: использует только ранги документов, игнорируя "уверенность" каждого retriever'а.

**Решение DBSF**: нормализация скоров к общей шкале [0, 1] через min-max scaling.

**Формула:**

```
# Шаг 1: Min-Max нормализация для каждого retriever'а
norm_score_vector = (score - min_vector) / (max_vector - min_vector)
norm_score_bm25   = (score - min_bm25)   / (max_bm25   - min_bm25)

# Шаг 2: Взвешенная сумма
dbsf_score(doc) = α × norm_score_vector + β × norm_score_bm25
```

где `α = β = 0.5` (равные веса).

**Преимущества DBSF:**
- Учитывает распределение скоров, а не только порядок
- Документ с высоким скором от одного retriever'а получит приоритет
- Позволяет тонко настраивать веса α и β

**Сравнение RRF vs DBSF:**

| Аспект | RRF | DBSF |
|--------|-----|------|
| Входные данные | Ранги | Скоры |
| Формула | `1/(c + rank)` | `α × norm_a + β × norm_b` |
| Чувствительность к шкале | Нет | Да (нормализация) |
| Настраиваемость | Только `c` | Веса `α, β` |

### 4.2 Интерпретация метрик

#### Hit@k (Recall@k)
Доля запросов, для которых целевой фильм найден в top-k.

- **Hit@1**: в 73% случаев `hybrid_dbsf` ставит правильный фильм на 1 место
- **Hit@10**: 94% запросов успешны — только 6 из 100 не найдены в top-10
- **Вывод**: гибридные методы дают +1% Hit@10 по сравнению с vector

#### MRR@k (Mean Reciprocal Rank)
Среднее значение `1/rank` для найденных документов.

- **Лучший MRR@10**: `hybrid_dbsf` = 0.816
- **Интерпретация**: в среднем целевой фильм на позиции ~1.2 (очень хорошо)
- **BM25 отстаёт**: MRR=0.649 — средняя позиция ~1.5

#### nDCG@k (Normalized Discounted Cumulative Gain)
Учитывает позицию релевантного документа с логарифмическим дисконтированием.

- **Лучший nDCG@10**: `hybrid_dbsf` = 0.848
- **DBSF > RRF**: 0.848 vs 0.828 — нормализация скоров улучшает ранжирование

#### Coverage
Доля уникальных документов в выдаче по всем запросам.

- **Hybrid методы**: ~69% корпуса покрыто
- **Vector only**: 64% — менее разнообразная выдача

#### Latency
Время выполнения одного запроса.

- **BM25**: 4.5 ms — в 40 раз быстрее vector
- **Vector**: 172 ms — время на embedding + Qdrant query
- **Hybrid**: 176 ms — незначительный overhead на fusion

## 5. Анализ ошибок

### 5.1 Кейсы провала (5 примеров)

#### ❌ Ошибка 1: "День сурка" — NOT FOUND

| Параметр | Значение |
|----------|----------|
| **Вопрос** | "Помоги вспомнить фильм, где главный герой застрял в одном и том же дне." |
| **Ожидаемый фильм** | День сурка |
| **Rank** | `null` (не найден в top-10) |
| **Top-5 выдачи** | Поток, Люди Икс: Первый класс, Пианист, Шоу Трумана, Приключения Тинтина |

**Причина**: Описание слишком абстрактное ("застрял в дне"). Конкуренты (Шоу Трумана, Поток) семантически близки по теме "ловушки".

**Как улучшить**: Добавить ключевые слова в описание фильма: "повторяющийся день", "временная петля".

## 6. Выводы

### Ключевые результаты

1. **Лучший метод: `hybrid_dbsf`**
   - Hit@10 = 94%, MRR@10 = 0.816, nDCG@10 = 0.848
   - DBSF превосходит RRF за счёт учёта скоров, а не только рангов

2. **Vector retrieval vs BM25**
   - Vector: Hit@10=93%, latency=172ms
   - BM25: Hit@10=79%, latency=4.5ms
   - Vector лучше для семантического поиска, BM25 — для точного лексического

3. **Гибридные методы**
   - Улучшают Hit@10 на 1% по сравнению с vector alone
   - Уменьшают not_found с 7% до 6%

4. **Основные проблемы**
   - 6% запросов не находят целевой фильм в top-10
   - Слишком общие вопросы и семантическая близость конкурентов

## 7. Рекомендации по улучшению

### Краткосрочные (low-hanging fruit)

| Улучшение | Ожидаемый эффект | Сложность |
|-----------|------------------|-----------|
| **Query expansion** через LLM | +2-3% Hit@10 | Низкая |
| **Тюнинг весов DBSF** (α, β) | +1% MRR | Низкая |
| **Увеличить top_k до 20** | -2% not_found | Низкая |

### Среднесрочные

| Улучшение | Ожидаемый эффект | Сложность |
|-----------|------------------|-----------|
| **Re-ranker (cross-encoder)** | +5% Hit@1 | Средняя |
| **Лемматизация для BM25** (pymorphy3) | +3% Hit@10 для BM25 | Средняя |
| **Метаданные в фильтрах** (год, жанр) | Точнее выдача | Средняя |

### Долгосрочные

| Улучшение | Ожидаемый эффект | Сложность |
|-----------|------------------|-----------|
| **Fine-tuning embedding модели** | +5-10% Hit@10 | Высокая |
| **Многоязычный BM25** (ru + en) | Лучше coverage | Высокая |
| **Learned sparse retrieval** (SPLADE) | +5% vs BM25 | Высокая |

#### `hit` — Hit Rate / Recall@k
```json
"hit": {
  "1": 0.73,   // 73% запросов: целевой фильм на 1 месте
  "3": 0.89,   // 89% запросов: целевой фильм в top-3
  "5": 0.93,   // 93% запросов: целевой фильм в top-5
  "10": 0.94   // 94% запросов: целевой фильм в top-10

```

**Интерпретация:**
- В 73 из 100 случаев система ставит правильный фильм на 1 место
- В 94 из 100 случаев целевой фильм находится в top-10
- Только 6 запросов (6%) полностью провалились

**Почему важно:**
- Hit@1 критичен для UX — пользователь хочет видеть ответ сразу
- Hit@10 показывает "потолок" системы — сколько запросов в принципе решаемы

---

#### `mrr` — Mean Reciprocal Rank@k
```json
"mrr": {
  "1": 0.73,
  "3": 0.805,
  "5": 0.815,
  "10": 0.8164285714285714  // ≈ 0.816
}
```

**Формула:** `MRR = (1/N) × Σ(1/rank_i)` для найденных документов

**Интерпретация:**
- MRR@10 = 0.816 означает: в среднем целевой фильм на позиции `1/0.816 ≈ 1.23`
- Очень хороший результат — почти всегда в top-2
- MRR@1 = Hit@1 (по определению)

**Почему важно:**
- Учитывает не только факт нахождения, но и позицию
- Чем выше MRR, тем меньше пользователю нужно скроллить

---

#### `ndcg` — Normalized Discounted Cumulative Gain@k
```json
"ndcg": {
  "1": 0.73,
  "3": 0.8270208679642892,  // ≈ 0.827
  "5": 0.8442479302872248,  // ≈ 0.844
  "10": 0.8475812636205581  // ≈ 0.848
}
```

**Формула:** 
```
DCG = Σ rel_i / log2(i + 1)
nDCG = DCG / IDCG (идеальный DCG)
```

**Интерпретация:**
- nDCG@10 = 0.848 — качество ранжирования на 84.8% от идеала
- Логарифмическое дисконтирование: позиция 1 в 3 раза важнее позиции 7
- nDCG строже чем Hit@k — учитывает распределение релевантности

**Почему важно:**
- Стандартная метрика для оценки ранжирования в IR
- Позволяет сравнивать системы даже при одинаковом Hit@k

---

#### `mean_rank` — Средняя позиция целевого документа
```json
"mean_rank": 1.3936170212765957  // ≈ 1.39
```

**Интерпретация:**
- В среднем целевой фильм находится на позиции 1.39
- Считается только для найденных документов (94 из 100)
- Чем ближе к 1.0, тем лучше

**Связь с MRR:**
- MRR ≈ 1/mean_rank, но не точно (разные формулы усреднения)
- mean_rank = 1.39 → MRR ≈ 0.72 (приблизительно)

---

#### `not_found` — Доля ненайденных запросов
```json
"not_found": 0.06  // 6%
```

**Интерпретация:**
- 6 из 100 запросов не нашли целевой фильм в top-10
- Это "провал" retrieval — LLM не получит нужный контекст
- `not_found = 1 - Hit@10`

**Почему важно:**
- Критическая метрика для RAG — без контекста LLM галлюцинирует
- Цель: минимизировать not_found

---

#### `coverage` — Покрытие корпуса
```json
"coverage": 0.689727463312369  // ≈ 69%
```

**Формула:** `coverage = |unique_docs_returned| / |corpus|`

**Интерпретация:**
- 69% документов корпуса (329 из 477) были возвращены хотя бы раз
- Остальные 31% — "мёртвые" документы, которые никогда не показываются

**Почему важно:**
- Низкий coverage = система "застряла" на популярных документах
- Высокий coverage = разнообразная выдача

---

#### `latency_ms` — Время выполнения запроса
```json

```

**Интерпретация:**
- Среднее время на один запрос: 176 мс

**Разбивка по компонентам:**
- Vector retrieval: ~172 ms (97% времени)
