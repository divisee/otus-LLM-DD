## 1. Введение

Данный отчёт описывает эксперименты по оценке качества **retrieval-компоненты** RAG-системы для подбора фильмов. 

**Цель**: сравнить различные методы поиска и выбрать оптимальную конфигурацию для production.

**Датасет**:
- **Корпус**: 477 фильмов из Kinopoisk/IMDb
- **Вопросы для оценки**: 100 запросов разной сложности (1-5)
- **Формат вопросов**: косвенные описания фильмов без упоминания названий, актёров, цитат

## 2. Методология

### 2.1 Архитектура Retrieval

```
┌─────────────────────────────────────────────────────────────┐
│                        Query                                 │
└─────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
┌─────────────────────────┐     ┌─────────────────────────┐
│   Dense Retriever       │     │   Sparse Retriever      │
│   (Qdrant + Ollama)     │     │   (Qdrant BM25)         │
│   cosine similarity     │     │   server-side inference │
└─────────────────────────┘     └─────────────────────────┘
              │                               │
              └───────────────┬───────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    Score Fusion                              │
│   ┌─────────────┐   ┌─────────────┐                         │
│   │     RRF     │   │    DBSF     │                         │
│   │  (по рангам)│   │ (по скорам) │                         │
│   └─────────────┘   └─────────────┘                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│              Top-K Documents (ranked)                        │
└─────────────────────────────────────────────────────────────┘
```

**Компоненты:**

| Компонент | Технология | Описание |
|-----------|------------|----------|
| Vector Store | Qdrant | Хранение dense и sparse эмбеддингов, ANN-поиск |
| Dense Embeddings | Ollama (embeddinggemma) | Локальная модель для генерации плотных векторов |
| Sparse Embeddings | Qdrant (BM25) | Server-side генерация разреженных векторов |
| Fusion | RRF / DBSF | Объединение результатов двух retriever'ов |

### 2.2 DBSF — Distribution-Based Score Fusion

**Проблема RRF**: использует только ранги документов, игнорируя "уверенность" каждого retriever'а.

**Решение DBSF**: нормализация скоров к общей шкале [0, 1] через min-max scaling.

**Формула:**

```
# Шаг 1: Min-Max нормализация для каждого retriever'а
norm_score_vector = (score - min_vector) / (max_vector - min_vector)
norm_score_bm25   = (score - min_bm25)   / (max_bm25   - min_bm25)

# Шаг 2: Взвешенная сумма
dbsf_score(doc) = α × norm_score_vector + β × norm_score_bm25
```

где `α = β = 0.5` (равные веса).

**Преимущества DBSF:**
- Учитывает распределение скоров, а не только порядок
- Документ с высоким скором от одного retriever'а получит приоритет
- Позволяет тонко настраивать веса α и β

**Сравнение RRF vs DBSF:**

| Аспект | RRF | DBSF |
|--------|-----|------|
| Входные данные | Ранги | Скоры |
| Формула | `1/(c + rank)` | `α × norm_a + β × norm_b` |
| Чувствительность к шкале | Нет | Да (нормализация) |
| Настраиваемость | Только `c` | Веса `α, β` |

### 2.1.1 Dense vs Sparse Vectors

В системе используются два типа векторных представлений для retrieval:

**Dense Vectors (плотные векторы):**
- **Генерация**: Локально через Ollama (embeddinggemma, размерность 1024)
- **Хранение**: В Qdrant как `dense` vector с cosine similarity
- **Применение**: Семантический поиск по сходству
- **Преимущества**: Высокая точность для парафраз и абстрактных запросов
- **Недостатки**: Высокая latency (172ms), требует GPU/CPU для генерации
- **Пример**: Запрос "фильм про любовь премьер-министра" → находит "Реальная любовь"

**Sparse Vectors (разреженные векторы):**
- **Генерация**: Server-side в Qdrant с моделью `Qdrant/bm25`
- **Хранение**: В Qdrant как `bm25` sparse vector (индексы слов + TF-IDF веса)
- **Применение**: Лексический поиск по ключевым словам
- **Преимущества**: Низкая latency (4.5ms), не требует локальных вычислений
- **Недостатки**: Менее точен для семантических запросов, чувствителен к опечаткам
- **Пример**: Запрос "бандиты философские беседы" → находит "Криминальное чтиво"

**Сравнение производительности:**

| Метрика | Dense (vector_rag) | Sparse (bm25) | Hybrid (dbsf) |
|---------|-------------------|---------------|---------------|
| Hit@10 | 93% | 67% | **95%** |
| Latency | 308ms | 7.1ms | 315ms |
| Coverage | 64% | 56% | 69% |

**Гибридный подход**: Комбинация dense + sparse через DBSF даёт лучший баланс точности и скорости.

### 4.2 Эксперимент с чанкингом

Сравнение влияния **рекурсивного чанкинга** на качество retrieval:

| Параметр | Значение |
|----------|----------|
| Chunk size | 500 символов |
| Overlap | 100 символов |
| Коллекция без чанкинга | `movies` (477 документов) |
| Коллекция с чанкингом | `movies_chunked` (634 чанка) |

#### Результаты сравнения

| Метрика | Без чанкинга | С чанкингом | Разница |
|---------|--------------|-------------|---------|
| **Hit@10** | 93.0% | **96.0%** | **+3.0%** ✅ |
| **MRR@10** | 0.806 | **0.827** | **+0.021** ✅ |
| **nDCG@10** | 0.836 | **0.860** | **+0.024** ✅ |
| **Not Found** | 6.0% | **4.0%** | **-2.0%** ✅ |
| **Latency (ms)** | 179.1 | 177.2 | -1.9 |

#### Почему чанкинг улучшает результаты

1. **Более точные embeddings**: короткие чанки (500 символов) создают более сфокусированные векторы
2. **Лучшее покрытие**: разные части описания фильма индексируются отдельно
3. **Overlap сохраняет контекст**: перекрытие в 100 символов не теряет информацию на границах

#### Статистика коллекции

```
movies (без чанкинга):
- Документов: 477
- Средняя длина текста: 426 символов

movies_chunked (с чанкингом 500/100):
- Чанков: 634
- Среднее чанков на фильм: 1.33
```

### 4.3 Интерпретация метрик

#### Hit@k (Recall@k)
Доля запросов, для которых целевой фильм найден в top-k.

- **Hit@1**: в 73% случаях `hybrid_dbsf` ставит правильный фильм на 1 место
- **Hit@10**: 94% запросов успешны — только 6 из 100 не найдены в top-10
- **Вывод**: гибридные методы дают +1% Hit@10 по сравнению с vector

#### MRR@k (Mean Reciprocal Rank)
Среднее значение `1/rank` для найденных документов.

- **Лучший MRR@10**: `hybrid_dbsf` = 0.762
- **Интерпретация**: в среднем целевой фильм на позиции ~1.3 (очень хорошо)
- **BM25 отстаёт**: MRR=0.551 — средняя позиция ~1.8

#### nDCG@k (Normalized Discounted Cumulative Gain)
Учитывает позицию релевантного документа с логарифмическим дисконтированием.

- **Лучший nDCG@10**: `hybrid_dbsf` = 0.810
- **DBSF > RRF**: 0.810 vs 0.790 — нормализация скоров улучшает ранжирование

#### Coverage
Доля уникальных документов в выдаче по всем запросам.

- **Hybrid методы**: ~69% корпуса покрыто
- **Vector only**: 64% — менее разнообразная выдача

#### Latency
Время выполнения одного запроса.

- **BM25**: 4.5 ms — в 40 раз быстрее vector
- **Vector**: 172 ms — время на embedding + Qdrant query
- **Hybrid**: 176 ms — незначительный overhead на fusion

## 5. Анализ ошибок

### 5.1 Кейсы провала (5 примеров)

#### ❌ Ошибка 1: "День сурка" — NOT FOUND

| Параметр | Значение |
|----------|----------|
| **Вопрос** | "Помоги вспомнить фильм, где главный герой застрял в одном и том же дне." |
| **Ожидаемый фильм** | День сурка |
| **Rank** | `null` (не найден в top-10) |
| **Top-5 выдачи** | Поток, Люди Икс: Первый класс, Пианист, Шоу Трумана, Приключения Тинтина |

**Причина**: Описание слишком абстрактное ("застрял в дне"). Конкуренты (Шоу Трумана, Поток) семантически близки по теме "ловушки".

**Как улучшить**: Добавить ключевые слова в описание фильма: "повторяющийся день", "временная петля".

## 6. Выводы

### Ключевые результаты

1. **Лучший метод: `hybrid_dbsf`**
   - Hit@10 = 95%, MRR@10 = 0.762, nDCG@10 = 0.810
   - DBSF превосходит RRF за счёт учёта скоров, а не только рангов

2. **Vector retrieval vs BM25**
   - Vector: Hit@10=93%, latency=308ms
   - BM25: Hit@10=67%, latency=7.1ms
   - Vector лучше для семантического поиска, BM25 — для точного лексического

3. **Гибридные методы**
   - Улучшают Hit@10 на 2% по сравнению с vector alone
   - Уменьшают not_found с 7% до 5%

4. **Основные проблемы**
   - 6% запросов не находят целевой фильм в top-10
   - Слишком общие вопросы и семантическая близость конкурентов

**Почему важно:**
- Hit@1 критичен для UX — пользователь хочет видеть ответ сразу
- Hit@10 показывает "потолок" системы — сколько запросов в принципе решаемы

#### `mrr` — Mean Reciprocal Rank@k
```json
"mrr": {
  "1": 0.73,
  "3": 0.805,
  "5": 0.815,
  "10": 0.762
}
```

**Формула:** `MRR = (1/N) × Σ(1/rank_i)` для найденных документов

**Интерпретация:**
- MRR@10 = 0.762 означает: в среднем целевой фильм на позиции `1/0.762 ≈ 1.31`
- Очень хороший результат — почти всегда в top-2
- MRR@1 = Hit@1 (по определению)

**Почему важно:**
- Учитывает не только факт нахождения, но и позицию
- Чем выше MRR, тем меньше пользователю нужно скроллить

---

#### `ndcg` — Normalized Discounted Cumulative Gain@k
```json
"ndcg": {
  "1": 0.73,
  "3": 0.827,
  "5": 0.844,
  "10": 0.810
}
```

**Формула:** 
```
DCG = Σ rel_i / log2(i + 1)
nDCG = DCG / IDCG (идеальный DCG)
```

**Интерпретация:**
- nDCG@10 = 0.810 — качество ранжирования на 81.0% от идеала
- Логарифмическое дисконтирование учитывает порядок — ранние позиции важнее

**Почему важно:**
- Показывает, насколько хорошо система ранжирует релевантные документы
- Высокий nDCG означает, что пользователю не нужно просматривать много страниц результатов

---

#### `mean_rank` — Средний ранг
```json
"mean_rank": 1.39
```

**Интерпретация:**
- Средний ранг целевого фильма среди всех запросов
- Значение ~1.39 говорит о том, что в среднем фильм находится на 1.39 позиции (очень хорошо)

**Почему важно:**
- Позволяет быстро оценить, насколько хорошо система в целом
- Чем ниже средний ранг, тем лучше

#### `not_found` — Доля не найденных запросов

```json
"not_found": 0.05
```

**Интерпретация:**

**Почему важно:**
- Позволяет оценить, насколько система полна и разнообразна
- Высокий процент not_found может указывать на проблемы с покрытием

#### `coverage` — Покрытие корпуса
```json

```

**Интерпретация:**
- Около 69% документов из корпуса были найдены хотя бы по одному запросу
- Это значение показывает, насколько разнообразна выдача системы

**Почему важно:**
- Высокое покрытие означает, что система может предложить пользователю больше вариантов
- Помогает избежать ситуации, когда пользователь видит одни и те же документы по разным запросам

#### `latency_ms` — Задержка в миллисекундах

**Почему важно:**
- Низкая задержка критична для пользовательского опыта
- Высокая задержка может привести к тому, что пользователи будут ждать ответа слишком долго
