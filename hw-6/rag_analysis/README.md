## Подготовка данных для оценки LLM
Данные для оценки формируются скриптом `hw-6/rag_analysis/generate_questions.py` на основе `hw-6/data/data_films.csv`. Для каждого фильма берутся поля `Title` и `Description Kinopoisk`, после чего LLM генерирует вопрос в стиле «Найди/Вспомни фильм…» с уровнем сложности от 1 до 5.

**Промпт (системный контекст):**
- Стиль: запрос на поиск фильма («Найди фильм…», «Вспомни фильм…»).
- Ограничения: не упоминать название, персонажей, актеров, цитаты или год.
- Сложность: от 1 (почти пересказ) до 5 (максимально косвенно).
- Длина: короткий вопрос (до 20–25 слов).

**Модель:**
- По умолчанию используется `gpt-4o-mini` из `hw-6/config.yaml` (можно переопределить параметрами в конфиге или через `OPENAI_API_KEY`).

**Выход:**
- CSV `hw-6/rag_analysis/data/rag_questions.csv` с колонками: `title`, `description`, `question`, `difficulty`.

# Оценка качества retrieval для RAG-подбора фильмов

Этот модуль оценивает **качество подбора (retrieval)** фильмов по вопросу: нашёлся ли нужный фильм в выдаче, на каком он месте, насколько стабильно ранжирование.

Датасет вопросов: `hw-6/rag_analysis/data/rag_questions.csv`.
- `question` — запрос пользователя
- `title` — **таргет** (ожидаемое название фильма)
- `difficulty` — сложность вопроса (1..5)

Важно: тут оцениваем **только retrieval** (поиск/ранжирование кандидатов), **без** оценки финального ответа LLM.

---

## Эксперименты

Все эксперименты запускаются одним скриптом и пишут результаты в разные подпапки.

### 1) `vector_rag` — простой векторный RAG
Источник: `hw-6/tools_rag.py` (`RagRetriever.retrieve`).
- Эмбеддинг запроса: Ollama `/api/embed` (`embedding_model` из `hw-6/config.yaml`)
- Поиск: Qdrant `query_points` по вектору
- Возвращается `top_k` документов с payload, включая `title`, `text_ru`, `genres`, etc.

Ограничения текущей реализации:
- используется `score_threshold=0.3` (может уменьшать recall при сложных вопросах)

### 2) `bm25_text_ru` — BM25 по полю `text_ru`
Лексический поиск по корпусу `text_ru` (описание фильма, payload в Qdrant).
- Корпус документов скачивается из Qdrant через `scroll` (payload only) один раз на прогон
- BM25 считается локально (быстро для текущего размера датасета ~477)

### 3) `hybrid_rrf` — ансамбль BM25 + vector через RRF
**Reciprocal Rank Fusion (RRF)** объединяет ранги из двух списков:

`rrf_score(doc) = Σ 1 / (c + rank_i(doc))`, где `c=60`, `rank_i` — позиция документа в выдаче i-го ретривера.

Почему RRF:
- устойчив, даже если скоры Qdrant и BM25 несопоставимы по масштабу
- работает «из коробки» без калибровки

---

## Метрики

Мы считаем метрики «нашёлся ли нужный фильм» и «на каком он месте».

### Базовые retrieval-метрики (для нескольких k)
Считаем для `k ∈ {1, 3, 5, 10}` (настраивается):
- **Hit@k**: есть ли таргетный фильм в топ-k
- **MRR@k**: `1/rank`, если фильм найден в топ-k, иначе 0
- **nDCG@k**: DCG/IDCG по бинарной релевантности (релевантен = title совпал)

### Диагностика ранга
- `rank`: позиция таргетного фильма в выдаче (1-based), либо `None`
- `median_rank`, `mean_rank` по найденным
- `not_found_share`: доля не найденных

### Метрики матчинга названия
Таргетный `title` сравниваем с `title` в payload:
- `title_exact@1`: нормализованное точное совпадение top-1
- `title_soft@1`: «мягкое» совпадение top-1 (Jaccard по токенам >= 0.8 или containment)

Нормализация для title:
- lower, trim, `ё→е`, токенизация по буквенно-цифровым токенам

## Артефакты / что сохраняем

Для каждого эксперимента создаётся папка:

`hw-6/rag_analysis/out/<experiment>/<run_name>/`

Внутри:
- `per_query.jsonl` — одна строка на запрос, с `rank`, `top_titles`, `top_ids`, матчингом
- `per_query.csv` — то же в табличном формате
- `summary.json` — агрегированные метрики + metadata эксперимента + trace_ids Langfuse (если включено)

## Скоры (похожесть) в результатах

Во всех `per_query.*` теперь сохраняются **сырые скоры**, чтобы можно было анализировать не только попадание в топ, но и «уверенность» ретривера:

- `top_vector_scores` — Qdrant similarity score (для `vector_rag`)
- `top_bm25_scores` — BM25 score (для `bm25_text_ru`)
- `top_rrf_scores` — RRF score (для `hybrid_rrf`)

Также есть унифицированные поля:
- `top_scores` + `top_score_fields` — удобный “default” скор для текущего эксперимента.

Примечание: скоры **не обязательно сопоставимы по масштабу** между методами (особенно vector vs bm25), поэтому для сравнения методов используем rank-based метрики (Hit/MRR/nDCG), а скоры — для диагностики/калибровки порогов.

## Возможности Qdrant, которые мы используем/учитываем

Qdrant в этом проекте хранит точки (фильмы) с:
- **вектором** эмбеддинга (по `Description Kinopoisk`)
- **payload** (метаданные), включая:
  - `title`, `year`, `genres`, `country`, `rating_kinopoisk`, ...
  - `text_ru` — русское описание (оно же `Description Kinopoisk`)

Что полезно для retrieval экспериментов:
- `query_points` — быстрый ANN поиск по вектору
- `scroll` — выгрузка payload всех документов (используем для построения BM25 корпуса)
- `score_threshold`, `limit (top_k)` — параметры качества/скорости
- payload может быть использован для фильтрации (genre/year/country) — потенциальные будущие эксперименты

- `vector_rag` — только векторный поиск (Qdrant)
- `bm25_text_ru` — только лексический BM25 по `text_ru`

### Сравнительная таблица метрик

> Важно: сравнивать «сырые» скоры между методами нельзя (разные шкалы). Для сравнения используем метрики ранжирования: Hit/MRR/nDCG.

### Короткий разбор

- **Лучший Hit@10 и nDCG@10** показал `hybrid_rrf` (0.94 / 0.847) — гибрид стабильно «дотягивает» нужный фильм в топ за счёт объединения сильных сторон векторного и лексического поиска.
- `vector_rag` даёт почти такой же Hit@10 (0.93), но **чуть хуже** по nDCG@10 и Mean rank — иногда целевой фильм оказывается ниже в выдаче.
- `bm25_text_ru` заметно проигрывает (Hit@10=0.79) и имеет **большую долю не найденных** (0.21). Это ожидаемо: вопросы часто перефразируют сюжет/сущности, и лексический матчинг без семантики срабатыет хуже.

### Почему получились такие результаты

- **Vector retrieval** хорошо работает на перефразированиях и косвенных описаниях (семантическое сходство). Поэтому у `vector_rag` высокий recall (Hit@10≈0.93). Проблема — иногда в топе оказываются «семантически похожие» по жанру/настроению фильмы, а таргет уезжает ниже (просадка nDCG и отдельные кейсы rank>1).
- **BM25** чувствителен к словоформам, порядку слов и наличию точных токенов. В вопросах у нас часто нет прямых сущностей (имён/цитат/актеров) и есть косвенные пересказы, поэтому BM25 хуже по recall и часто вместо таргета поднимает документы с совпадением по общим словам (пример: «герой», «главная героиня», «в будущем», «полиция»).
- **Hybrid RRF** выигрывает, потому что:
  - если таргет найден хотя бы одним из ретриверов в топе, RRF обычно подтягивает его выше;
  - RRF устойчив к несопоставимым шкалам скоров (vector vs bm25) — объединяем только ранги.

### Что лучше использовать в проде

- В качестве дефолта для RAG-поиска по таким вопросам **лучше `hybrid_rrf`**: максимум стабильности и лучший баланс (и по Hit@10, и по рангу).
- Если нужна простота/скорость и нет смысла поддерживать BM25-корпус — можно оставить **`vector_rag`** (разница небольшая), но стоит подумать о re-ranker (см. ниже).
- **Только BM25** на таких данных использовать не стоит — слишком большой `not_found_share`.

### Как можно улучшить (идеи)

**1) Предобработка текста для BM25 (лемматизация + стоп-слова) — да, имеет смысл.**

Поскольку BM25 — лексический метод, нормализация сильно помогает:
- лемматизация/стемминг русских словоформ (например, `pymorphy3` или `natasha`) повышает шанс совпадения «схожих» форм,
- удаление стоп-слов снижает шум и уменьшает вклад общих слов,
- нормализация `ё→е`, приведение к lowercase, удаление пунктуации.

Важно: делать одинаковую обработку **и для корпуса**, и для **запроса**.

**2) Улучшить эмбеддинги / модель**
- подобрать более сильную embedding-модель (особенно для RU),
- проверить, соответствует ли язык эмбеддинга языку текста (RU vs EN),
- если есть ресурсы — сделать fine-tuning / domain-adaptation на кино-сюжетах.

**3) Добавить re-ranker (cross-encoder / LLM-rerank)**
- схема: retrieval (vector/hybrid) → 50 кандидатов → rerank (BGE reranker / LLM judge) → top-10.
- это обычно даёт заметный прирост именно Hit@1 и nDCG.

**4) Query expansion / переформулировка запроса**
- короткий LLM шаг «переформулируй вопрос в набор ключевых фактов» может помочь BM25,
- можно сохранять 2 версии запроса: семантическую и ключевую.

**5) Тюнинг параметров retrieval**
- для `vector_rag`: проверить влияние `score_threshold` (слишком высокий порог режет recall в сложных вопросах),
- поднять `top_k` на этапе retrieval (например, 20–50) и срезать после re-rank.
